# IceBot System Architecture

IceBot is an automated ice cream kiosk system that combines a cloud platform with edge processing. The system includes applications for administration, kiosk ordering, centralized business processing, and on-site device control. The components coordinate through the network connections and device communications shown in the system architecture diagram.

IceBot Backend is built with ASP.NET Core and deployed in a K3s Cluster on the production server. The Backend manages organizations, stores, kiosks, product catalogs and configuration, orders, payments, reporting, monitoring, deployment coordination, and execution-state synchronization. PostgreSQL stores business data, while MinIO stores Lua files. Both are deployed in the K3s Cluster. The Backend communicates with PostgreSQL over the PostgreSQL protocol via TCP and accesses MinIO through an S3-compatible API over HTTP.

Admin Web is a Next.js/React application deployed on Vercel. It provides the kiosk management interface, allows users to upload Lua files to the system, and communicates with the Backend over HTTPS. Flutter Kiosk App displays the menu, allows customers to select items, and sends orders to the Backend over HTTPS.

In the system architecture diagram, Flutter Kiosk App and IceBot Edge Runtime are represented as two separate application blocks. Kiosk App is responsible for customer interaction, while Edge is responsible for order execution and hardware control. The two applications may be deployed on the same device or on separate devices. Kiosk App can run on a tablet or computer, including Windows, provided that the platform is supported by the Flutter Kiosk App build. Edge Runtime currently runs on a Windows computer. Kiosk App does not directly control the robot or peripheral machines.

IceBot Edge Runtime is responsible for on-site robot execution, communication with peripheral machines, storing the execution state of each ice cream unit on the device, and sending operational reports to the Backend. During kiosk deployment configuration synchronization, Edge downloads Lua files from MinIO over HTTPS and stores them locally for subsequent orders. When the Backend receives an order from Kiosk App, it determines the list and execution order of the Lua files required. Edge actively pulls execution commands from the Backend over HTTPS, using mTLS for authentication, through the private network provided by NetBird. The command contains order information and the ordered list of Lua file names. Edge reads the local Lua files, converts supported Lua instructions into an execution plan, and then calls the Fairino SDK and corresponding plugins to control the robot and peripheral machines. Edge does not download Lua again for each order; it synchronizes programs when the deployment configuration is updated. Ordering and control flows still pass through the Backend whether the two applications run on the same device or on separate devices.

Edge stores the execution state of each ice cream unit and operational logs on the device to support recovery after an interruption, such as a power outage or application failure. Staff must handle the interrupted product, inspect the work area, and restart Edge according to the operating procedure. The system then remakes the interrupted unit from the beginning while retaining units recorded as completed. Execution reports are stored locally and sent to the Backend again after the connection is restored.

Edge controls the Fairino FR5 robot controller through the Fairino SDK over an Ethernet connection. Peripheral machines connect to Edge through RS485. The system supports integrating multiple machine types when the device has a compatible RS485 protocol, documented control protocol, and corresponding plugin driver on Edge. The ice cream machine, coffee machine, and cup dispenser are examples of devices that can be integrated; they are not an exhaustive list of supported device types.

The Backend connects to external services over HTTPS. Firebase supports authentication and sends notifications through FCM. PayOS provides payment processing and sends payment results to the Backend through an HTTPS webhook. After payment is confirmed, the Backend updates the order status and creates an execution command for Edge; sending the command to Edge is a separate flow from the payment webhook.

Fairino Studio belongs to the Simulation Tools group. It allows users to prepare and simulate robot workflows and then export them as Lua files. Users upload these Lua files to the system through Admin Web. This is a manual operational flow; Fairino Studio does not participate directly in the production runtime.

AI Service is shown in the External Services group of the diagram. The frontend calls an external AI API to provide chatbot functionality.
